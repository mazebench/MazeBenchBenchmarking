# O×O unintended momentum

The supplied 58-command sequence originally reproduced the issue on its last Right:

```text
U Rx3 D Rx9 Ux4 R U Lx7 D L U Rx4 Dx4 L Ux3 R U Lx4 D Lx2 Ux2 Rx5
```

Before the fix, the player moved one tile while both interlocked blue bodies
moved three tiles right and fell one level. The room is `k4sogtzyju.json`.
The imported engine now moves the player and both bodies **one tile right in
one tick, without a fall**. All other objects retain their pre-command state.
`report.json` records the fixed replay and controls; the exact current engine
provenance is maintained in [upstream.json](../../engine/v1/upstream.json).

## Cause

The three remote ramps at `(14,12,1)`, `(14,13,1)`, and `(14,14,1)` select the
slope-aware push path for the whole room, even though this push touches no ramp.
In `MazeBenchEngineUnitTest/engine/src/physics/tick.inc`, the `slope_scene`
branch calls `TranslateSlopeMomentumObjects` for ordinary deliberate pushes.

Previously, the departing-support loop in `engine/src/physics/slope_motion.inc`
gave a body horizontal momentum when its proposed destination was above a cell
another moving body vacated, without requiring a slippery support. Here group
0's voxel `(8,3,4)` proposes
`(9,3,4)`, directly above group 1's departing voxel `(9,3,3)` (engine coordinates).
It receives rightward inherited momentum even though neither body is on Ice.
`StoreSupportedMandatoryMomentum` in `command_state.inc` accepts that inherited
flag as sufficient to schedule another object-motion tick.

The same false momentum is queued on the fourth Right, but its continuation is
blocked. The fifth push takes group 1's foot from `(9,5,1)` to `(10,5,1)`
(Benchmarking coordinates), beyond the raised orange support. The body can then
be carried along by the interlocked group 0. The two extra translations take
the assembly off its remaining raised supports, so gravity drops it.

Controlled changes to the exact pre-push state, before the fix:

| Variant | Result of one Right |
| --- | --- |
| Original room | Three tiles right, then one level down |
| Only the three distant ramps replaced with walls | One tile right |
| Ramps retained; one wall added at `(10,5,0)` | One tile right |

The user's existing `test-556` originally behaved similarly: its Up had one tick;
adding a single isolated right-facing ramp at `(9,9,1)` produced three Up
translations followed by a fall. These comparisons ran in memory, without
changing the user's room or UnitTesting project.

## Exact reproduction files

- `before-fifth-right.unit-test.json`: the complete room immediately before
  move 58. Input is Right; expected is independently constructed by moving the
  player and the two blue bodies one tile. The repaired engine passes.
- `no-ramps-control.unit-test.json`: same setup with only the distant ramps
  replaced by walls. It still satisfies its one-tile expectation.
- `test-556-remote-ramp.unit-test.json`: a copy of the user's similar test with
  the remote ramp added and its original expected single-push result retained.
- `report.json`: observed coordinates, timings in engine ticks, and parity checks.

These are individual native `voxelbench-compact-test-v1` files, suitable for
adding to UnitTesting's split project. They are not replacement project bundles.
The sibling project now includes these three reproductions, normalized to its
canonical Up input, plus 20 new interlocked-body and clone regression cases.

Reproduce from the Benchmarking repository:

```sh
node scripts/reproduce-oxo-momentum.mjs
```

The script compares all 58 commands, frame by frame, between connected Play
physics and the isolated sibling WASM. It also round-trips the single-command
fixture through UnitTesting's actual test adapter and checks the controls.
It asserts one tick, one tile, no fall, and unchanged unrelated objects.
Pass `--output diagnostics/oxo-momentum` to regenerate the O×O fixtures/report
from the current authored room. The test-556 copy is a captured diagnostic,
not regenerated by this command.

The imported engine source and WASM matched the recorded upstream snapshot
during the investigation. The differing behavior was caused by room
geometry selecting an engine path, not by different engine binaries, extra
input commands, connected-room transitions, or animation interpolation.

The upstream fix requires slippery support for departing-support inheritance.
The expanded native, WASM, visual, and terrain-isolation tests retain coverage
of legitimate ramps, carried stacks, and blocked transactions. The same audit
also repaired clone vacancy checks and exact gate search. Project-owned editor,
Solutions, and world-solver wrappers preserve the new gate-state flag; the
canonical source and WASM remain byte-identical to upstream.
